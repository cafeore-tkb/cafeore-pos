# Feature Specification: 提供時間モデル（stack モデル）の当日当てはめタブ

**Feature Branch**: `feat/pos-dashboard-stack-model`

**Created**: 2026-10-20

**Status**: Draft

**Input**: User description: "この環境に、dashboardの機能を追加します。現状ではページを選択する方式のdashboardが構築されています。そこに、追加で1ページを作成してください。これは、このブランチの名前の通り、additonalな内容となります。ですので、既存のページに追加ではなく、新規でタブを作る方針です。追加する内容としては、 /Users/rysato/dev/sohosai-analysis/2025/nisui/cafeore_analysis にある、Stack杯数による提供時間の予測モデルを、現状のデータで常にfitして、各種係数の様子から、店舗のオペレーションの様子を観察する機能を追加する、といった内容となります。"

## 背景

- 店舗運営ダッシュボード（`/dashboard`）は、用途ごとのページをナビで選ぶ方式で、いまは 6 ページある（売り上げ／提供パフォーマンス／消費量・在庫／個別データ／運用記録／25年度比較）。
- 解析リポジトリ（cafeore_analysis）には **stack モデル**がある。注文の時点で「受付済みだが、まだ提供可能になっていないドリンクの杯数」（stack）を使って、その注文の提供時間を予測するモデルである。

  ```
  予測提供時間(分) = max( b × (stack − a1) + c1,  c1 )      b = b1 + c1 / N
  ```

  - 係数の意味は次のとおり。
    - `a1`（杯）: 平坦部のしきい値。stack がこれ以下なら、提供時間は伸びない。
    - `c1`（分）: 最低提供時間。空いているときの所要時間を表す。
    - `b`（分/杯）: 混雑による伸び。しきい値を 1 杯超えるごとに加わる時間。
    - `N`: 抽出担当の人数。
  - 現在のレジは、雙峰祭2025 の実績で当てはめた**固定の係数**で待ち時間の予測を出している。
- 本機能は、ダッシュボードに**新しいタブ**を 1 つ足す。既存のページには手を入れない。タブでは、その日の実データでこのモデルを継続的に当て直し、係数とその推移を示す。目的は次のように店舗のオペレーションの状態を読み取れるようにすることである。
  - 「最低提供時間が延びている」
  - 「何杯までなら待ちが伸びずにさばけているか」
  - 「混んだときの 1 杯あたりの伸びが大きい」

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 当日データで当て直した係数と現在の状況を見る (Priority: P1)

現場統括者や遠隔のオーナーがダッシュボードを開き、新しいタブ「提供時間モデル」を選ぶ。

- 画面には、選択中の日・期間の注文で当てはめた係数（a1・c1・b、および b1・N）が表示される。
- 当てはめの基になった件数、いまの stack、いま注文したときの予測提供時間も表示される。
- 注文が受け付けられたり、提供可能になったりすると、ページを再読み込みしなくても当てはめと表示が更新される。

**Why this priority**: 「現状のデータで常に fit して係数を見る」という依頼の中核であり、これだけで店舗の速さ（c1）・さばける量（a1）・混雑への弱さ（b）を当日の実測で読める。

**Independent Test**: 次の 2 つで確かめられる。

- 当日の注文がある状態でタブを開き、係数・件数・いまの stack・予測が表示されることを見る。
- 別端末で注文を提供可能にしたあと、係数が自動で更新されることを見る。

**Acceptance Scenarios**:

1. **Given** 選択中の日に、提供時間が確定した注文が 20 件以上ある, **When** 利用者が「提供時間モデル」タブを選ぶ, **Then** 次が表示される。
   - モデル式
   - 係数 a1・b1・c1・N・b
   - 当てはめに使った注文の件数と、まだ提供可能になっていない注文の件数
   - いまの stack（杯）と、いま注文したときの予測提供時間（分）
2. **Given** タブを表示している, **When** 別の端末である注文が提供可能になる, **Then** 画面は再読み込みなしで更新される。当てはめの件数が増え、係数はその注文を含めて当て直した値になる。
3. **Given** 選択中の日に提供時間が確定した注文が 20 件未満しかない, **When** タブを表示する, **Then** 「当てはめ不能（件数不足）」と、あと何件で当てはめるかが表示される。係数の代わりに、比較用の固定モデル（レジの予測と同じ係数）の値と、その予測だけが表示される。
4. **Given** どの初期値でも当てはめが収束しない, **When** タブを表示する, **Then** 「当てはめ不能（収束しない）」と表示され、係数の欄に数値は出ない。誤った数値は出さない。

### User Story 2 - 実測とモデル曲線を重ねて当てはまりを確かめる (Priority: P2)

利用者は次の図表を見て、係数がどの程度信用できるかを判断する。

- 散布図: 各注文の注文時点の stack（横軸、杯）と実測の提供時間（縦軸、分）。当てはめた曲線と、レジの固定モデルの曲線を重ねる。
- 精度の要約: 平均絶対誤差など。stack を使わず一律に平均で予測した場合や、固定モデルで予測した場合と並べる。

**Why this priority**: 係数だけでは、外れ値や件数の少なさに引っ張られた値かどうかが分からない。観察の結論を誤らないための裏付けになる。

**Independent Test**: 当日の注文が十分ある状態で、次の 2 点を確かめる。

- 散布図に当てはめた注文の点がすべて描かれ、2 本の曲線が重なっていること。
- 精度表の 3 行（当てはめ／固定モデル／一律平均）が表示されること。

**Acceptance Scenarios**:

1. **Given** 当てはめに成功している, **When** 利用者がタブの散布図を見る, **Then** 次が表示される。
   - 当てはめに使った全注文の点
   - 当てはめた曲線と、固定モデルの曲線（凡例で区別する）
   - 折れ点 a1 の位置
2. **Given** 当てはめに成功している, **When** 利用者が精度の欄を見る, **Then** 「この当てはめ」「固定モデル」「一律に平均」の 3 通りについて、次が並ぶ。
   - 件数
   - 平均残差（実測 − 予測。正なら予測より遅い）
   - 平均絶対誤差
   - 絶対誤差の中央値
3. **Given** 点にカーソルを合わせる、またはタップする, **When** 点が選ばれる, **Then** その注文の注文番号・stack・実測提供時間・予測提供時間が数値で表示される。

### User Story 3 - 係数の時間推移からオペレーションの変化を読む (Priority: P3)

営業後や毎時の引き継ぎで、利用者はその日の係数の変化を見る。

- 推移の作り方: 選択中の期間を集計間隔（15／30／60 分）ごとに区切り、各区切りの終わりの時点で「そこまでのデータで当て直した」係数を求める。
- 見方の例: 「昼のピークのあとに c1 が上がった」「人員交代のあとに傾き b が大きくなった」のように、オペレーションの変化を時刻と結びつけて読む。

**Why this priority**: 「各種係数の様子から店舗のオペレーションの様子を観察する」には、ある時点の値だけでなく変化が要る。ただし P1・P2 だけでも当日の状態は読めるので、優先度は下げる。

**Independent Test**: 過去の営業日（注文が数百件ある日）を選び、次の 2 点を確かめる。

- 時刻を横軸にした a1・c1・b の推移が、集計間隔ごとの点として表示されること。
- 最後の点が User Story 1 の係数と一致すること。

**Acceptance Scenarios**:

1. **Given** 選択中の期間に当てはめ可能な時点が 2 つ以上ある, **When** 利用者が推移の欄を見る, **Then** a1・c1・b がそれぞれ別のグラフに、集計間隔ごとの時点で表示される。比較用に、固定モデルの値が基準線として表示される。
2. **Given** ある時点ではまだ件数が足りない、または収束しない, **When** 推移を表示する, **Then** その時点は点を打たず、欠けていることが分かる表示にする。0 や直前の値で埋めない。
3. **Given** 推移を表示している, **When** 利用者が表示条件の集計間隔を 15 分から 60 分に変える, **Then** 推移の点の間隔が 60 分に変わる。

---

### User Story 4 - 抽出担当の人数を変えて傾きを試算する (Priority: P3)

利用者は、当てはめに使う抽出担当の人数 N を実際の体制に合わせて指定する。さらに、N±1 人にしたときの傾き b と予測提供時間の試算表を見る。

**Why this priority**: 次の 2 つの理由で必要になる。

- b1 は N に依存するので、記録として正しい N を当てはめに使う必要がある。
- 「1 人増やしたら」という問いに答える材料になる。

ただし、当てはめた曲線そのものは N に依らないので、観察の中核ではない。

**Independent Test**: N を 6 から 5 に変え、次の 2 点を確かめる。

- a1・c1・b が変わらず、b1 だけが変わること。
- N 別の試算表の値が式どおりであること。

**Acceptance Scenarios**:

1. **Given** 当てはめに成功している, **When** 利用者が人数 N を変える, **Then** 次のように表示が変わる。
   - b1 は変わる。a1・c1・b（当てはめた曲線）は変わらない。
   - N−1・N・N+1 人の傾き b と、代表的な stack（例: 0・a1・10・20・30 杯）での予測提供時間が表で表示される。
2. **Given** 当てはめた b1 が負である, **When** N 別の表を表示する, **Then** 「N が ○ 人を超えると傾き b が 0 以下になる」という注意を表示する。
3. **Given** 試算表を表示している, **When** 利用者が表を読む, **Then** 表の近くに「人数に反比例して傾きが緩和されるのはモデルに置いた仮定であり、試算である」という注意が表示されている。

---

### Edge Cases

- **未完了の注文**: まだ提供可能になっていない注文（提供可能の時刻が無い）は、stack には数え、当てはめには使わない（提供時間が確定していないため）。
  - 営業中は直近の混んだ時間帯の注文ほど未完了で残りやすく、傾きを低めに見積もりやすい。この注意を常に表示する。
- **取消された注文**: 当てはめに使わない。stack には、受付から取消までの間だけ数える。
- **時刻の逆転**: 提供可能の時刻が受付の時刻より前の注文は、壊れた記録として当てはめから外し、外した件数を表示する。
- **外れ値**: 極端に長い提供時間（打刻忘れが疑われる数十分のもの）は**除外しない**。散布図の表示範囲だけは、外れ値で軸が広がりすぎないように調整してよい。その場合は「表示範囲外に ○ 件」と明記する。
- **当てはめの不安定さ**: 次の場合は、係数の近くに警告を出す。
  - a1 がデータの stack の範囲外にある。
  - 傾き b が 0 以下になる。
- **外挿**: 観測された最大の stack を超える予測は外挿であることを、試算表と「いま注文したときの予測」に示す。
- **営業日のまたぎ**: stack は、その注文と同じ営業日（JST）に受け付けた注文だけで数える。打刻忘れで前日以前に残った未完了の注文は、当日の stack に数えない。そのような注文があれば、件数を「打刻忘れの可能性」として表示する。
- **ドリンクを含まない注文**: グッズのみの注文は杯数 0 なので、stack を増やさない。当てはめには使う（解析リポジトリの既定に合わせる）。
- **データ未受信**: 接続前・再接続中で注文をまだ受け取っていないときは、「0 件」ではなく「未受信」と表示する。
- **未来の期間**: 表示条件が未来や逆転している場合は、他のページと同じエラーを出し、図表を隠す。

## Requirements *(mandatory)*

### Functional Requirements

**タブと表示条件**

- **FR-001**: ダッシュボードのページ選択（広い画面の左ナビ、狭い画面の上部の選択欄）に、新しいページ「提供時間モデル」を 1 つ追加しなければならない。
  - 既存の 6 ページの内容・並び・既定の表示ページは変えてはならない。
  - 追加するページは既存ページと同じ操作で切り替えられること（矢印キーによる切り替えを含む）。
- **FR-002**: 新しいページは、ダッシュボード共通の表示条件（JST の日付・開始時刻・終了時刻・集計間隔）に従わなければならない。
  - 当てはめの対象は「表示条件の期間内に受け付けた注文」とする。
  - stack は、期間の開始前に受け付けた同じ営業日の注文も含めて数える。

**当てはめ**

- **FR-003**: 当てはめに使うモデル式と既定は、解析リポジトリの既定に合わせなければならない。
  - モデル式: `予測提供時間 = max(b × (stack − a1) + c1, c1)`、`b = b1 + c1 / N`
  - 当てはめ方: 非線形最小二乗、等重み、外れ値の除外なし
- **FR-004**: 各注文の stack と提供時間は、次のように定めなければならない。
  - stack: その注文を受け付けた瞬間に、同じ営業日に受け付け済みで、まだ提供可能になっていない先行注文のドリンク杯数の合計。
  - ドリンク杯数: 作るカップの数。グッズは含まず、セットは構成する杯数で数える。
  - 提供時間: 注文の「提供可能になった時刻 − 受付時刻」（分）。注文単位で、全カップがそろった時刻を使う。
- **FR-005**: 当てはめは、表示条件の期間のデータが変わるたびにやり直さなければならない。データが変わるのは、注文の追加・取消、提供可能・お渡しの打刻、表示条件の変更のときである。
- **FR-006**: 当てはめには、当てはめに使える注文が 20 件以上必要である。
  - 初期値は複数の候補を順に試し、最初に収束したものを使う（解析リポジトリと同じ候補）。
  - 件数不足または収束しないときは、その理由を示し、係数を表示してはならない。
- **FR-007**: 抽出担当の人数 N は利用者が画面で指定できなければならない。
  - 既定値は 6 人とする（雙峰祭2025・2026 年の体制）。
  - N を変えたとき、b1 と N 別の試算は変わり、当てはめた曲線（a1・c1・b）は変わらないこと。

**表示**

- **FR-008**: 係数の欄に、次を表示しなければならない。
  - a1（杯）・b1・c1（分）・N（人）・b（分/杯）
  - 当てはめに使った件数・未完了の件数・除外した壊れた記録の件数
  - 当てはめの時点（最後にデータを反映した時刻）
- **FR-009**: 「いまの状況」として、次を表示しなければならない。
  - いまの stack（その営業日に受け付け、まだ提供可能になっていない注文のドリンク杯数の合計）
  - いま注文したときの予測提供時間（当てはめたモデルと固定モデルの両方）
  - 未完了の注文のうち、いちばん古いものの経過時間
  - 表示条件の終わりが過去の場合は、「いま」の代わりに期間末の時点での値として表示する。
- **FR-010**: 比較用の**固定モデル**として、レジの待ち時間予測で使っているのと同じ係数（雙峰祭2025 の当てはめ）を、係数・曲線・予測・精度の各所に並べて表示しなければならない。
- **FR-011**: stack を横軸、提供時間を縦軸にした散布図を表示しなければならない。
  - 散布図には、当てはめた曲線、固定モデルの曲線、折れ点 a1 を重ねる。
  - 点を選ぶと、その注文の注文番号・stack・実測・予測が数値で分かること。
- **FR-012**: 精度の要約を表示しなければならない。
  - 対象: 「この当てはめ」「固定モデル」「stack を使わず一律に平均」の 3 通り
  - 項目: 件数・平均残差・平均絶対誤差・絶対誤差の中央値
- **FR-013**: stack を一定の幅（例: 2 杯）で区切った区間ごとに、次を表で表示しなければならない。
  - 実測提供時間の中央値と 10%・90% 点
  - 区間の中央での予測値
- **FR-014**: 係数の時間推移（a1・c1・b）を、集計間隔ごとの時点のグラフで表示しなければならない。
  - 各時点の値は、期間の開始からその時点までに見えていたデータで当て直したものとする。その時点より後に付いた打刻は使わない。
  - 当てはめ不能な時点は、空けて表示する。
- **FR-015**: N−1・N・N+1 人の傾き b と、代表的な stack での予測提供時間の試算表を表示しなければならない。
- **FR-016**: 次の警告・注意を、該当するときに係数の近くに表示しなければならない。
  - 警告: a1 がデータの stack の範囲外である、傾き b が 0 以下である、b1 が負で N の上限がある、外挿である、打刻忘れの可能性がある注文がある。
  - 常時の注意（3 点）:
    - 未完了の注文は当てはめに入らず、傾きを低めに見積もりやすい。
    - 人数への反比例は仮定である。
    - 実測は観察であって、原因を断定するものではない。

**全般**

- **FR-017**: 係数の意味は、平易な言葉で表示しなければならない。厳密な式や定義は折り畳みで確認できるようにする。
  - a1: 「待ちが伸び始める杯数」
  - c1: 「空いているときの提供時間」
  - b: 「1 杯増えるごとに延びる時間」
- **FR-018**: 本機能はダッシュボードが既に受け取っている注文データだけを使い、新しいデータの保存や書き込みを行ってはならない。
  - 当てはめの結果を、レジの待ち時間予測に自動で反映してはならない。
- **FR-019**: 担当者の個人名（品目の担当者の記入欄、注文コメント）を、このページに表示・使用してはならない。
- **FR-020**: すべての図表の軸に対象と単位を付けなければならない。
  - 主要な値は、数値（表または選択時の表示）でも確認できること。
  - 色だけで系列を区別させないこと（凡例・線種・文字を併用する）。

### Key Entities *(include if feature involves data)*

- **当てはめ用の注文観測**: 1 注文 1 行。次を持つ。
  - 注文番号・受付時刻
  - 注文時点の stack（杯）
  - 提供時間（分）。未完了なら無い。
  - ドリンク杯数・取消の有無・営業日
- **当てはめ結果**: 係数 a1・b1・c1、人数 N、実効傾き b、件数（当てはめ・未完了・除外）、収束の可否と不能の理由、対象のデータ範囲（stack の最小・最大）、当てはめの時点。
- **固定モデル**: レジの待ち時間予測と同じ係数の組（雙峰祭2025、N = 6）。比較の基準として使い、本機能からは変更しない。
- **係数の推移点**: 集計間隔ごとの時点と、その時点までのデータでの当てはめ結果（不能なら欠測）。
- **精度の要約**: 予測のしかたごとの件数・平均残差・平均絶対誤差・絶対誤差の中央値。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 解析リポジトリの既定の当てはめと、有効数字 3 桁で一致する係数が得られる。
  - 入力: 雙峰祭2025 の実績データ（978 件、N = 6）
  - 期待値: a1 = 7.28 杯、b1 = −0.554、c1 = 5.99 分、b = 0.444 分/杯
- **SC-002**: 提供可能の打刻が入ってから 10 秒以内に、新しいページの係数と「いまの状況」がその打刻を含む値に更新される。
- **SC-003**: 1 日分の注文（1,000 件程度）を表示した状態でも、ページの切り替えや表示条件の変更から 2 秒以内に、係数・散布図・推移が表示される。
- **SC-004**: 既存の 6 ページの表示内容と操作は、本機能の追加前後で変わらない。
- **SC-005**: 店舗運営に関わる利用者が、ページの表示だけを見て次の 3 つの問いに答えられる。
  - 「空いているときの提供時間は何分か」
  - 「何杯までなら待ちが伸びないか」
  - 「1 杯増えると何分延びるか」
- **SC-006**: 当てはめ不能な状況（件数不足・収束しない）で、誤った係数の数値が表示されることがない。

## Assumptions

- 利用者と権限は、既存のダッシュボードと同じとする（閲覧のみ以上）。本機能は読み取りだけで、認証・認可の境界は変えない。
- タブの名前は「提供時間モデル」とし、既存 6 ページの後ろに置く。名前は計画時に見直してよい。
- 抽出担当の人数 N は、画面上の入力で与える（既定 6 人）。シフトや CaOS の担当者から自動で数えることは、本機能の範囲外とする。指定した N を端末に記憶するのは、利便のための任意の動作とする。
- 「常に fit する」は、ダッシュボードが受け取っている注文データが変わるたびに、表示条件の範囲で当て直すことと解釈する。最新の値は、期間の開始からの累積で当て直したものとする。直近 1 時間だけで当てるような移動窓の当てはめは範囲外とし、変化は係数の推移（FR-014）で読む。
- 固定モデルの係数は、レジの待ち時間予測と同じ値を参照する。値は一か所で定め、二重に持たない。
- 当てはめのやり方（モデル式・初期値の候補・最小件数・等重み・外れ値を除外しないこと）は、解析リポジトリ（cafeore_analysis の R/model_svtime.R・R/quickview.R、チケット T-84）の既定を正とする。違いが出たら解析リポジトリに合わせる。
- 過去の日付を選んだ場合も、現在サーバーにある注文とカップから再集計した値を使う。当時の画面に出ていた値の復元ではない。
- 25年度比較のための同梱データ（雙峰祭2025）を新しいページで当てはめて見せることは、本機能の範囲外とする。SC-001 の検証データとして使うことは想定する。
- 解析リポジトリにある範囲外の機能（待ち行列シミュレーション、プラトー領域の分布の解析、担当者別の解析）は、このページに含めない。
