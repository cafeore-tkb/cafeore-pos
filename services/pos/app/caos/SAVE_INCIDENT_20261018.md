# 2026-10-18 マスターシート保存不具合の調査

時刻は日本時間。本番 `/master-sheet` を開いた iPad Safari に USB で接続し、再読み込みせずに確認した。

## 確認できたこと

1. コメントの既読情報に含まれる NUL（`U+0000`）をログの `details` として送ると、本番 API は HTTP 500 を返した。同じログの NUL を文字として表したものは HTTP 204 で保存できた。PostgreSQL の `jsonb` は NUL を受け付けない。
2. iPad の localStorage にログ6,482件が滞留していた。最後の記録は12:32。17:42の確認では、1文字を書くだけでも両方のタブで `QuotaExceededError` が出た。確認用の独立したキー以外は変更していない。
3. 片方のタブのメモリに、永続保存できなかった操作115件とログ3,239件が残っていた。操作は16:31〜17:07の割当・統合・着手・完了などで、このタブに `outbox.send` と送信権取得の記録はなかった。
4. もう片方のタブは15:35に送信権を取得し、15:36に非表示になっていた。メモリ上の操作キューは空で、ログ553件が残っていた。
5. Web Locks の一覧でも、`cafeore:caos-outbox:` を保持するタブと、同じロックを待つタブが確認できた。

旧実装では localStorage への保存失敗をメモリへの退避で成功扱いにしていた。メモリはタブ間で共有されないため、送信権を持つタブは、別タブに退避した操作を読めない。画面には操作が反映されても API へ送られず、再読み込みするとそのタブのメモリを失う経路になる。

## 保全とDBへの救出

- 両タブの保存領域、メモリ上のログ・操作、読み込んだアセット、ロック状態を Mac に保存した。
- 合計10,274件のログを API 経由でDBへ保存し、書き出しを読み直して `(tabId, sequence)` が全件存在することを確認した。
- このうち115件の `outbox.enqueued` に未送信操作の内容があり、保全した115件の操作IDすべてをDBのログと照合した。
- 現行APIが受け付けない NUL を含む35件は、救出時にNULを文字として表し、元の details の JSON も残した。端末・Macの元データは削除していない。
- ログの保存と、盤面への操作の適用は別。古い操作115件を盤面へ一括適用していない。適用する場合は最新の注文・提供状態と競合を確認する必要がある。
- すでに再読み込みで失われたメモリの内容まで復元できたとはいえない。過去の担当列・時刻を推測で作成しない。

## 対応

- 操作は永続保存に成功したものだけ受け付け、保存失敗時は通知する。
- 送信権は送信処理中だけ取得する。旧版が保持するロックと名前を分ける。
- 保存待ち件数と送信失敗理由を画面に出す。
- NULを含む旧ログは、API側で元の details の JSON を文字列に包んで `jsonb` に保存し、GET・書き出しで復元する。通常のログとAPI応答の構造は維持する。
- 5秒ごとのDB書き込みを追加するだけでは、ログのHTTP 500・保存容量不足・タブ間の送信権待ちは解消しない。

## 配信時刻との関係

15:31前後に配信されたPRは名前・検索・ダッシュボード等の変更で、当該時間帯のmainにマスターの送信キュー・端末保存・API接続先の直接変更は見つからなかった。最も時刻が近い更新だけを原因としない。配信後も、開いているタブのJavaScriptは再読み込みまで置き換わらない。
