# ドリップ所要時間の実績補正（要件ドラフト）

ステータス: 提案・レビュー待ち。実装は含まない。

## 目的

マスターシートで使う「1杯5分・2杯6分」の固定予測を、実際の盤面操作で記録された所要時間に合わせて徐々に補正する。
さらに、1時間のシフト内で観測した担当者ごとの速さを係数にして、タイムライン、残り時間、次に空く担当者の予測を改善する。

初期モデルは次の形に留める。

```text
予測所要時間 = 杯数別の標準時間 × 担当者の補正係数
例: 1杯の標準時間300秒 × 係数0.8 = 240秒
```

この数値は盤面上の進行を予測するための目安であり、抽出を自動で完了させたり、人の評価・順位付けに使ったりしない。
統計的な精度向上は未検証であり、過去実績による比較で確認する。

## 現状と既存のデータ

- `modules/common/src/lib/caos-board.ts` の `caosBrewSec` は、1杯300秒・2杯360秒を返す。
- `logic/queue.ts` はタイムライン、残り時間、次に空く列の予測に利用している。入れ替え時間は別の定数（15秒）。
- `logic/libero.ts`、`components/SidePanels.tsx` にも固定時間の参照がある。
- カップの `dripId` が1回の抽出を表す。同じカードの2杯には同じ開始・終了時刻がある。
- `brew_started_at` / `brew_finished_at` は盤面上の開始・終了。終了はCaOSの「次へ」で記録され、準備完了・提供完了とは異なる。
- `dripper_assignee_changes` は担当者の交代履歴を持つ。開始時点の担当者を復元する材料にできる。
- `caos_operations` / `caos_operation_cups` は成功した操作の履歴を残す。現行のカップが注文編集で削除・再作成される場合にも配慮が必要。
- 操作履歴は補正後の押下時刻とサーバー処理時刻を区別する。オフライン再送時の時刻の扱いは実装前に確認する。
- シフト予定は現在ブラウザーが読む。予定の境界で担当者を自動交代する仕組みではない。
- 担当者と予定表は名前ベースであり、安定した個人IDは現状のモデルにない。

既存の `DESIGN_REQUIREMENTS.md` §9 は固定時間・学習なしを現行仕様としている。本書はその変更案であり、採用時に現行仕様書・READMEも更新する。

## 必要な機能

### 1. 学習用の実績を作る

- 全ドリッパーの完了した抽出を集計し、1杯・2杯を分ける。
- 1回の抽出を1件として扱い、2杯抽出を2件として重複集計しない。
- 所要時間は、同じ抽出の終了時刻から開始時刻を引いて求める。提供完了時刻は使わない。
- 担当者は抽出開始時点の実際の担当者を使う。現在の列見出しや予定表だけで過去の担当者を推定しない。
- 開始・終了の欠損、時刻逆転、杯数や時刻の不整合、重複イベントを除く。
- 初期版では、キャンセル、淹れ直し、途中交代、抽出中の杯数変更、開始のやり直しなど、帰属や時間が曖昧な実績を除外する案とする。
- 担当者不明でも、時間と杯数が確実な通常抽出は全体の標準時間に利用できる。個人係数には利用しない。
- ブラウザー内のテストプレイを本番の学習データに混ぜない。オペ練と営業実績を混ぜるかは別途決める。
- 採用・除外理由を記録し、集計対象件数を確認できるようにする。

### 2. 標準時間を少しずつ補正する

- 1杯・2杯それぞれで外れ値を除外した後の算術平均を使う。
- 外れ値の判定は中央値とMAD（中央値からの距離の中央値）を使う方式を候補とする。
- 少数データ、MADが0になる場合、通常の平均が定義できない場合にも動作を定義する。
- 現行の300秒・360秒を初期値とし、少数の実績だけで大きく変化させない。
- 候補式: `標準時間 = (初期値の重み × 初期値 + 採用件数 × 実績平均) / (初期値の重み + 採用件数)`。
- 実績が増えるほど実績平均を重くする。初期値の重み、対象期間、外れ値の閾値は未決定。
- 速い人の実績を、現在の固定時間から離れているという理由だけで除外しない。

### 3. 担当者の係数で補正する

- 各実績を `実測時間 / その杯数の標準時間` に変換し、1杯と2杯を同じ尺度で集計する。
- 係数の初期値は1.0。速い担当者は1.0未満、遅い担当者は1.0超となる。
- 少数の実績では係数を1.0に近づけ、件数が増えるほど本人の実績を反映する。
- 候補式: `係数 = 1 + n / (n + 個人用の重み) × (実績比率の平均 - 1)`。
- 不明な担当者・新しい担当者・不足データの場合は全体の標準時間を使う。
- 1時間のシフト内での補正を想定する。ただし、予定の1時間枠、実際の担当交代、直近60分のどれを集計単位とするかは未決定。
- 標準時間と個人係数で同じ変化を二重に補正しないよう、基準モデルのバージョンと比率計算をそろえる。全体の係数の中心が1付近になることを検証する。
- 係数の上下限、学習を始める件数、前シフトからの引き継ぎは実績を見て決める。

### 4. 予測を各画面で統一する

- 共通の予測関数を通じて、タイムライン、残り時間、次に空く列、リベロ表示、標準予測の表示へ反映する。
- 完了済みカードの実時刻はモデル更新で変更しない。
- 抽出中のカードは開始時点の予測を保持し、後から別の実績が増えても残り時間を急変させない案とする。
- 待機カードには最新のモデルと現在の担当者を使う。未来の担当者が不明な場合の扱いを明示する。
- 入れ替え時間15秒は抽出時間と分離し、初期版では学習しない。
- 予測時間を過ぎても、自動で終了扱いにはしない。
- 「早すぎる次へ」「押し忘れ」などの警告は変更の影響を確認する。学習した予測値だけを外れ値・誤操作判定の根拠にして循環させない。
- モデル未取得・取得失敗時は、最後に確認できたモデル、または従来の固定値へフォールバックする。

## 実装構成の案

1. API側で成功した操作履歴などから抽出単位の実績を復元し、安定したキーで重複を除く。現行カップ表だけを正本にするかは、削除・再作成の影響を確認して決める。
2. API側で集計し、標準時間・係数・件数・対象期間・更新時刻・モデルバージョンを返す。複数端末・複数APIインスタンスで同じモデルを共有する。
3. 完了操作のDB更新を重い再集計で遅らせない。更新頻度、キャッシュ、永続化、再計算方法はデータ量を確認して選ぶ。
4. フロントエンドの共通関数にモデルを渡し、各画面が同じ結果を使う。抽出中カードの予測を端末再読込後も再現できる保存・復元方法を用意する。
5. 表示反映を切り替えられるようにし、まず集計結果と既存予測を比較してから有効にする。

## 懸念点・決めること

| 論点 | 懸念・判断が必要な内容 |
| --- | --- |
| 計測の意味 | 測れるのは盤面操作間の時間。押し忘れ、まとめ操作、作業開始前の割当は実際の抽出との差になる。 |
| 時刻の整合 | オフラインで遅れて届いた抽出操作と交代操作の前後関係を、サーバー処理順だけで決めない。判定不能なら個人集計から除く。 |
| 個人の識別 | 表記揺れ・同姓同名・名前変更。日をまたいで学習を引き継ぐなら個人IDの導入を検討する。 |
| シフトの定義 | 実際の担当交代を優先するが、交代履歴だけでは1時間の予定枠を確定できない。単なる毎正時リセットにはしない。 |
| 学習の期間 | 当日、直近数日、直近N件のどれを使うか。営業日・イベント・オペ練の分離が必要か。 |
| データの偏り | 担当者ごとの1杯/2杯比率、商品、ホット/アイス、混雑度が異なる。単純係数で説明できる範囲を確認する。 |
| 外れ値の除外 | 本当に速い/遅い人を除外する危険がある。閾値・最小件数・MADが0の場合の扱いを検証する。 |
| 予測超過 | 平均予測を過ぎた抽出の残り時間はこのモデルだけでは分からない。初期版は従来の超過表示を維持する案。 |
| 画面への説明 | 標準時間、個人係数、学習件数をどこまで表示するか。能力の断定と受け取られない文言にする。 |
| 履歴の不足 | 過去に交代や操作の記録がない期間は帰属を推測で埋めない。既存の実データ量はまだ確認していない。 |

## 検証・受け入れ条件

- 初期状態・実績0件では1杯300秒・2杯360秒、個人係数1.0で動く。
- 2杯の抽出を1件として集計し、再送・再集計でも件数が増えない。
- 外れ値、欠損、MADが0、少数実績、担当者不明、途中交代、開始やり直しを区別して処理できる。
- シフト境界と日付境界、遅延送信、注文編集・削除、複数端末の再接続で集計が壊れない。
- 同じ抽出の予測が各画面で一致し、モデル更新・再読込で抽出中の予測が不意に変わらない。
- API障害やモデル不足時にも盤面操作を継続できる。
- 過去データを時間順に再生し、その時点より前の実績だけで予測する。未来のデータを混ぜて精度を評価しない。
- 固定値、標準時間補正のみ、個人係数ありの3方式を比較する。平均絶対誤差、過小予測の割合、誤差の上位分位、杯数別・担当者別の偏りを確認する。
- 精度の合格基準やモデル有効化に必要な件数は、データ分布を見てレビューで決める。学習対象の採用率・除外理由も確認する。
