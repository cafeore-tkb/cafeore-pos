# CaOS の抽出終了予測・実績記録（要件ドラフト）

ステータス: 方針整理中。計算方法の数値は実績の検証後に決める。実装・運用開始はまだ行っていない。

## 目的

タイムラインの抽出終了予測を、マスターが実際に「次へ」を押すタイミングにできるだけ近づける。今年初導入するため、ある程度の精度を目指しつつ、短すぎる予測や急激な変動を抑える安全志向のシンプルなモデルとする。

記録されるのは盤面上の抽出開始から終了操作までの時間であり、物理的な抽出完了時刻ではない。予測を過ぎても自動完了せず、マスターが実際のタイミングで「次へ」を押す。記録は店舗の状態を振り返る手がかりにもするが、数値だけで原因や個人の能力を断定しない。

## 予測の方針

- 基本形は `店舗全体の杯数別標準時間 × 担当者の補正係数`。店舗全体の直近の変化と、その時点の店舗標準に対する個人の相対的な傾向を分けて管理する。
- 標準時間はホット1杯・ホット2杯・アイス1杯・アイス2杯の4種類を区別し、有効な直近実績から求める。ホットとアイスの混合2杯は運用上ない。各種類の件数が少ない場合の安全なフォールバックは実データで検証する。シフト交代やメニュー構成の変化には比較的早く追従し、平均、中央値、少し余裕を持たせる方式などを比較する。
- 有効な実績があれば早めに反映する。実績がない場合は現行の1杯300秒・2杯360秒を初期値にする。少数件時の急変をどう抑えるかは検証する。
- 個人実績はシフト間・日をまたいで使う。各実績の `実測秒数 ÷ その抽出時点の同じホット・アイス構成と杯数の店舗標準時間` を個人の比率として扱う案。種類・杯数を共通尺度で集計する。本人の実績が少ないときは係数を1.0に寄せ、件数に応じて徐々に反映する。例えば初期値に5件分の重みを置く案は検証用であり確定値ではない。
- 店舗標準はその実績より前に得られた情報を使う。モデルの計算時点・バージョンをそろえ、未来のデータや当該実績を混ぜて個人比率や精度を評価しない。店舗標準と個人係数は分けても、担当メニューなどの影響が完全に分離できるとは限らない。
- 前日練習で得た実績を使って、現行モデルの予測精度と外れ値・追従性を評価し、実測に基づいてモデルを調整する。1日目の実績を2日目の初期モデルに使うことも候補とする。集計対象・外れ値・件数・更新結果を確認してから反映し、当日中の直近実績にも追従させる。練習・営業データの取り扱いと翌日の自動反映か手動確認かは検証結果を踏まえて決める。
- 現行の待機カード間の入れ替え時間15秒は、実績ベースの予測を採用するときに加算しない。「次へ」は前の抽出の終了と次の開始を同時に記録する。タイムライン、残り時間、次に空く列、リベロ、標準予測などで同じ予測を使う。
- 待機カードは現在の担当者と最新モデルを使う。抽出中の予測をモデル更新時に更新するか固定するか、再読込・複数端末での一貫性を含めて決める。未来の交代は確定していないため、待機カードに現在の担当者を使うことを予測の前提とする。
- 取得失敗時は最後に確認できたモデル、なければ初期値にフォールバックし、盤面操作を妨げない。予測時間に依存する早すぎる「次へ」・押し忘れ警告への影響も確認する。

## 実績と担当者

- `dripId` 単位で1回の抽出を1件とし、2杯を二重に数えない。開始・終了時刻の欠損、時刻逆転、杯数・時刻の不整合、重複を区別する。
- 異なる注文の1杯ずつを抽出前に統合した場合も、同じ `dripId` の2杯からなる1回の2杯抽出として扱う。各カップの `iced_brew` を確認し、ホット2杯・アイス2杯を判別する。混合や種類不明など通常の4分類に入らない記録は推測せず集計から除外し、理由を残す。抽出開始後に統合されて杯数が変わった場合は、通常の2杯抽出と同一視せず除外候補とする。注文編集・削除後の過去の杯数や種類の復元可能性も検証する。
- 押し忘れ、緊急淹れ直し、途中交代、開始やり直し、抽出中の杯数変更など通常の時間として扱いにくい記録は適宜除外し、理由を残す。個別の除外ルールと閾値はデータを見て決める。
- 実際の担当交代履歴を使い、予定だけから過去の担当者を推測しない。途中交代は初期版では個人集計から除く。担当者不明でも時間と杯数が確かな通常抽出は店舗全体の集計に使える。
- 今年の名簿では同姓同名・同学年の衝突がない前提で、シフト配信の `name` と `grade` の組を個人の識別に使う。シフト間・日をまたいで引き継ぐ。自由入力・学年不明など確実に紐付けられないものは個人集計から除く。
- 現在のシフト配信には名前と学年があるが、CaOS の担当者と交代履歴には学年がない。交代候補から学年を保存・共有し、交代・入れ替え・履歴を通して維持する必要がある。旧データは学年を後から確実に復元できる場合だけ紐付ける。
- オフライン再送時は押下時刻とサーバー処理時刻を区別し、交代との前後関係が確定できない場合は個人に帰属させない。注文編集・削除・再作成後の操作履歴からの復元可能性を確認する。ブラウザー内テストプレイは本番学習に混ぜない。オペ練と営業の分離はデータを見て決める。

## 数値ログと店舗の振り返り

- 抽出ごとに、安定した抽出キー、開始・終了時刻、杯数、各カップのホット・アイスの構成、列、担当者の識別情報、実測秒数、採用・除外と理由を記録または再現可能にする。
- 予測の根拠として、予測時刻、店舗標準秒数、個人係数、予測秒数、対象件数・期間、モデルバージョンを残す。少なくとも抽出開始時の予測を記録する。抽出中に予測を更新する場合、開始時と「次へ」の直前の表示値を区別できるようにする。
- 実測と予測の差を後から計算できるようにし、更新時刻と採用件数を記録する。再送・再計算時の重複を防ぎ、元データとその時点の予測を区別する。
- 店舗単位で時間帯別の実測、予測誤差、件数、除外理由を確認できるようにする。待機件数など別の運用指標との比較は今後検討する。個人別の表示範囲・保存期間・アクセス権は実装時に決める。

## 検証と実装順

1. 操作履歴、カップ、担当交代履歴から実績を復元し、件数・欠損・除外理由、時刻と担当者の信頼性を調査する。1日目データの翌日利用が可能かも確認する。
2. 過去データを時系列で再生し、その時点より前のデータだけを使って、固定値、店舗標準のみ、個人補正ありを比較する。杯数別の誤差、過小予測率、上位分位、急な変化への追従、予測の揺れ、除外率を確認する。直近件数、統計量、個人への重み、外れ値の閾値、予測の余裕はこの結果で決める。
3. シフト配信から名前・学年を交代情報と履歴に保持する。旧データと手入力は曖昧な帰属を避ける。
4. 共通モデルと予測・実績ログを API 側で扱い、複数端末で整合させる。抽出完了操作を重い再集計で遅らせず、取得失敗時も操作を継続できるようにする。表示への適用は切り替え可能にし、比較検証してから有効化する。
5. タイムラインなど各画面に反映し、15秒加算、警告、テストプレイ、再読込・再送・日付境界を検証する。採用時は `DESIGN_REQUIREMENTS.md`、README、操作マニュアルを更新する。

## 受け入れ条件

- 0件時の初期値は1杯300秒・2杯360秒、個人係数1.0。有効実績は少数でも適切に反映し、外れ値や個人の1件目で極端に変化しない。
- 同じ抽出を再送・再集計しても1件として扱う。別注文の1杯ずつを統合したカードは2杯の抽出1件とし、ホット2杯・アイス2杯を区別できる。混合や種類不明は除外理由を確認できる。抽出中の統合や注文編集・削除も検証する。担当者不明、途中交代、緊急淹れ直し、開始やり直しを区別し、採用・除外理由を確認できる。
- シフト間・日をまたいで同じ名前・学年の実績を引き継ぐ。手入力や学年不明は推測して他人に結び付けない。1日目から2日目へのモデル更新は採用した運用に沿って確認できる。
- 各画面の予測が一致し、待機カード間の15秒を重複加算しない。予測を過ぎても自動完了せず、モデル取得失敗時も盤面操作を続けられる。
- 抽出開始時の予測と実測、店舗標準、個人係数、件数、モデルバージョンを後から確認できる。テストプレイを本番データに混ぜない。
- 時系列検証で未来のデータを使わず、固定値との比較を行う。数値の合格基準や運用開始条件は実データを確認して決める。
